name: do-issue
description: >
  GitHub Issue番号を指定すると、Issue内容を確認してタスクを遂行し、TDDで実装してPRまで作成する。
  ユーザーが "do-issue"、"issue対応"、GitHub Issue番号（例: #123、do-issue 123）を指定したときに使用する。
---

指定されたGitHub Issueの内容を `gh issue view <Issue番号>` で確認し、タスクを遂行せよ。タスクは以下の手順で進めろ

1. Issueに記載されている内容を理解する
2. 最新のデフォルトブランチにチェックアウトし、pullを行い(git pull origin main)、最新のリモートの状態を取得 (git submodule update --init --recursive も忘れずに行う)
3. 最新のデフォルトブランチをもとに新しいブランチを作成(ブランチ名にIssue番号を含めること) (`git checkout -b "opencode/fix-<Issue番号>"`)する
4. Issueの内容を実現するために必要なタスクをTDD（テスト駆動開発）に基づいて遂行する
5. テストとLintを実行し、すべてのテストが通ることを確認する
6. コミットを適切な粒度で作成する
   - コミットメッセージは日本語で作ること
   - **git add -Aやgit add .のような、すべての変更を一括でステージングするコマンドは使用厳禁。そんなことをするのは初心者だけです。変更を細かく確認し、必要な変更のみをステージングすること**
   - アドオンに関連する変更を行ったときは、コミットメッセージに`[Add-on]`を含めること　（例: `[toadflax] 〇〇の機能を追加`）
   - github issueに関連した変更を行ったときは、コミットメッセージにIssue番号を含めること　（例: `[#123] 〇〇のバグを修正`）
7. 以下のルールに従ってPRを作成する
   - PRのdescriptionにはIssueの内容、この機能またはPRが必要になった経緯、どのように実装したかを日本語で記載すること
   - アドオンに関連するタイトルの場合は、タイトルに`[Add-on]`を含めること　（例: `[kingston_sim] 〇〇の機能を追加`）
   - PRのdescriptionには`- Closes #<Issue番号>`と記載すること

## 注意点

- 必要以上に変更が多くなる場合(1000行を超えるなど)は実装方針が間違っている可能性がある。大規模改修が必要なときは実装前に必ず相談せよ。(但し, CI上のagentなど権限制限を外して実行している場合はこの限りではない)
- 変更を加える前に、Issueの内容を十分に理解すること
- 実装が終わってPRを作成したとしても、Issueに対しては絶対に手を加えないこと（勝手に閉じたりコメントしたりしないこと）。PRのレビュー、コメント、マージは人間が行うので、PRを作成した後は人間の判断を待つこと
